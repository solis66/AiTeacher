# 用户注册功能

## 一、需求概述
用户能够进行注册，将用户信息存储在 PostgreSQL 数据库中，并生成唯一的用户 ID。
注册成功后的账号即为系统的数据归属标识：所有个人数据（对话历史、批改记录、作文图片等）均以该账号为键进行隔离存储。

- **账户号码**：用户输入的 11 位手机号码（仅数字）。
- **密码**：用户输入的不小于 6 位的密码（可包含字母、数字、特殊字符）。
- **已有初始系统测试账号**：`13727575721`，密码 `123456`。

## 二、功能要求

### 1. 前端（注册页面）
- 登录页需提供「注册」入口，点击切换到注册表单。
- 注册表单字段：
  - 手机号（账户号码）：文本输入，最大长度 11。
  - 密码：密码输入框，支持显示/隐藏切换（复用现有登录页交互）。
  - 确认密码：密码输入框，用于二次确认。
  - 校验通过前的表单字段级错误提示（参考现有 LoginPage 的 `errors` 交互样式）。
- 前端即时校验规则（与后端口径一致，仅用于提升体验，不作为安全边界）：
  - 手机号：11 位且全为数字，否则提示「请输入11位手机号码」。
  - 密码：长度 ≥ 6，否则提示「密码长度不能少于6位」。
  - 确认密码：与密码不一致，提示「两次输入的密码不一致」。
- 提交前按钮置灰（`isLoading` 与 `isFormValid` 控制），禁止重复提交。
- 注册成功后：清除表单，跳转 / 回到登录页，提示「注册成功，请登录」，并预填手机号。

### 2. 后端（注册接口）
- 提供 `POST /register` 接口，请求体 `{"account": "...", "password": "...", "confirm_password": "..."}`（字段命名与前端一致，可与现有 `username`/`password` 兼容，见「一致性」章节）。
- 服务端必须再次做完整的输入校验（不信任前端）：
  - `account` 非空、11 位、纯数字。
  - `password` 非空、长度 ≥ 6、字符集合法。
  - `confirm_password` 与 `password` 一致。
  - 任一校验失败返回统一错误结构 `{'success': False, 'error': ...}`。
- 手机号查重：注册前查询数据库中该账号是否已存在；已存在返回「该手机号已注册」。
- 生成唯一用户 ID 并落库到 PostgreSQL 的用户表。
- 密码必须采用 **bcrypt 加盐哈希**存储（`bcrypt.hashpw`），**禁止明文存储、禁止复用现有 `hashlib.sha256(password.encode()).hexdigest()` 无盐方案**。当前 [api.py](file:///c:/Users/20931/Desktop/AiTeachers/backend/api.py) 的登录校验需改为从 PostgreSQL 读取同一套 bcrypt 哈希比对，保证注册数据能被登录正确校验。
- 注册接口不要求登录态（所有请求应放行）。

### 3. 接口统一
- 复用 [request_helpers.py](file:///c:/Users/20931/Desktop/AiTeachers/backend/utils/request_helpers.py) 中的 `get_json_body` / `json_error` / `json_ok`，错误响应与 `success` 结构保持一致。

## 三、数据约束

### 1. 账户号码（手机号）
| 约束项 | 规则 |
| --- | --- |
| 格式 | 中国大陆 11 位手机号，正则 `^1\d{10}$` |
| 字符 | 仅阿拉伯数字 0-9 |
| 长度 | 固定 11 位 |
| 唯一性 | 全局唯一，禁止重复注册 |
| 存储 | 用户表中作为账号唯一标识（主键或唯一索引） |
| 前后端 | 前端用同一正则校验，后端必须再校验 |

### 2. 密码
| 约束项 | 规则 |
| --- | --- |
| 最小长度 | ≥ 6 位 |
| 允许字符 | 英文字母（A-Z、a-z）、数字（0-9）、常见特殊字符（如 `!@#$%^&*()._-+` 等可见符号），空字符/空格不允许作为密码成分 |
| 禁止字符 | 中文及控制字符、不可见空白 |
| 存储 | **bcrypt 加盐哈希**，不回显、不记录日志、不随接口返回；bcrypt 结果串自带盐值，无需独立 `salt` 字段 |
| 算法 | Python `bcrypt` 库：注册用 `bcrypt.hashpw`，登录用 `bcrypt.checkpw`；注意 bcrypt 有 72 字节输入上限，对本项目手机号+密码场景无影响 |
| 校验 | 与确认密码字段完全一致 |

### 3. 用户 ID
| 约束项 | 规则 |
| --- | --- |
| 唯一性 | 全局唯一，注册时生成 |
| 生成方式 | **PostgreSQL 自增主键（BIGSERIAL）**，一经确定全项目统一 |
| 可见范围 | 仅后端用于关联可，不暴露给前端 UI；前端业务身份使用手机号 |

### 4. 用户表结构（PostgreSQL 定稿 DDL）
```sql
CREATE TABLE IF NOT EXISTS users (
    id BIGSERIAL PRIMARY KEY,            -- 唯一用户ID，自增
    account VARCHAR(11) NOT NULL UNIQUE, -- 手机号账号，11位，唯一
    password_hash VARCHAR(64) NOT NULL,  -- bcrypt 加盐哈希后的密码（结果串自带盐）
    created_at TIMESTAMPTZ NOT NULL DEFAULT now() -- 注册时间
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_account ON users(account);
```

## 四、一致性

项目采用「后端 PostgreSQL 用户表 + 前端 localStorage 认证态 + `X-Username` 请求头数据隔离」的分层设计，注册功能必须与既有机制保持一致，避免出现"能注册却无法正常使用/能登录但数据串号"的不一致问题。

### 1. 登录与注册的数据源一致
- 当前 [api.py](file:///c:/Users/20931/Desktop/AiTeachers/backend/api.py) 的 `USERS` 内存字典（仅含 admin）必须替换为从 PostgreSQL `users` 表读取，`/login` 校验逻辑改为「手机号 + bcrypt 哈希比对」。
- 注册写入的用户必须能被 `/login` 立即登录成功；已存在的账号 `/register` 必须报「已注册」。
- JWT 生成逻辑保持不变：`username` 字段填手机号，仍写入 `app.config['SECRET_KEY']`（密钥硬编码为既有约定，见项目记忆）。

### 2. 数据隔离键一致（手机号即 owner）
- 现有隔离依赖 `X-Username` 请求头：`get_request_username()` 读到的手机号将作为：
  - 对话历史文件：`backend/history/{手机号}_history.json`；
  - 批改记录：`review_store.py` 中 `reviews` 表的 `owner` 字段；
  - 作文图片等按 owner 隔离的资源。
- 因此注册账号（手机号）就是数据 owner，无需新增映射；禁止用用户 ID 作为存储键，否则与既有历史数据脱节。

### 3. 前端身份同步
- 注册成功后回到登录页，登录后 `setToken` / `setUser(手机号)`，`getOwnerHeader()` 以手机号填充 `X-Username`，保证后续接口按手机号取数。
- localStorage 键名沿用 [auth.js](file:///c:/Users/20931/Desktop/AiTeachers/frontend/src/utils/auth.js) 的 `TOKEN_KEY` / `USER_KEY`，不新增魔法字符串键。

### 4. 并发与幂等
- 手机号唯一约束由数据库唯一索引兜底；即使两个并发注册同一手机号，也只会成功一个，另一个返回「该手机号已注册」。应用层查重后仍需捕获唯一约束冲突，防止 500。

### 5. 测试账号一致性
- 存量测试账号 `13727575721`（密码 `123456`）属纯数字密码，按「密码可含数字」规则合法。存量账号旧方案为无盐 `hashlib.sha256`，新方案为 bcrypt，两者无法直接比对，需在首次登录时做兼容迁移：先用旧的 `sha256(password)` 校验，通过后立即将该账号改写为 bcrypt 哈希，否则存量账号登录会失败。

### 6. 数据一致性兜底原则
- 不使用随机/模拟数据（遵循项目约定）；注册与登录为真实 PostgreSQL 读写。
- 所有写入失败（数据库不可用、唯一冲突）必须返回明确错误，不得静默降级或用简单方式将就。
