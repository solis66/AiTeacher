# 记忆系统设计

> 适用范围：AiTeachers（Flask + Vue + SQLite/Chroma 的初中作文 AI 批改与咨询系统）
> 状态：P0 已实现并自检通过；P1 / P2 为设计稿
> 最后更新：2026-09-15

---

## 1. 结论

本项目**不缺存储，缺三样东西**：

1. **一个真实的用户实体** —— 现在 `owner` 是登录账号（教师），`get_user_id` 返回假随机 ID，学生维度在数据模型里还不成立。
2. **一条把记忆读回提示词的路径** —— 聊天历史已经落盘，但从不进模型。
3. **一个从批改结果里提炼特征的环节** —— `reviews` 表存着每次批改的全部教学数据，目前零个性化使用。

因此设计的第一原则：**不要把"记忆"当成一个东西**。拆成三条独立链路，各自有不同的存储、生命周期与注入点。

## 2. 现状盘点

以下事实均已核对源码，行号以改造前版本为准。

### 2.1 对话链路是无状态的

| 事实 | 位置 |
|---|---|
| `answer_question(question)` 只接收一个问题字符串，无 session / owner 参数 | `services/consultation_service.py:704` |
| `input_dict = {"messages": [{"role": "user", "content": query}]}` —— 单条消息，历史从不进入模型 | `agent/tools/react_agent.py:264-268` |
| `create_agent` 只在 `_init_agent` 里创建一次，`system_prompt=load_system_prompts()` 为静态内容 | `agent/tools/react_agent.py:90-95` |

第三点决定了**每用户记忆不能塞进 system prompt**：要么每个请求重建 agent（把毫秒级请求变成秒级），要么改数据不动结构。

### 2.2 历史已经存在，但只服务 UI

| 事实 | 位置 |
|---|---|
| 聊天历史落盘为 `history/{username}_history.json`，上限 100 条 | `api.py:1537-1652` |
| 提供 `/save_history`、`/get_history`、`/delete_history` 三个接口 | `api.py:1591-1657` |
| 前端读取后仅按 `isDateWithinWeek` 过滤 7 天，用于侧边栏展示 | `src/components/MainPage.vue:476-487` |

**这份数据从未被送回模型。** 用户问"我刚才那个问题呢"，模型完全不知道在指什么。

### 2.3 用户标识只停留在脚手架

```python
user_id = ["1001", "1002", ...]

@tool(description="获取用户的ID, 以纯字符串形式返回")
def get_user_id() -> str:
    return random.choice(user_id)          # agent/tools/agent_tools.py:22-24
```

返回随机 ID，且没有任何下游逻辑消费它。**这类"让模型自己决定调用工具来获取记忆"的设计是反模式**，详见 §8。

另外 `/chat` 路由用 `request.headers.get('X-Username', 'anonymous')` 归属数据（`api.py:1352`），而前端这个请求**曾经漏传该请求头**，导致所有咨询数据都落到 `anonymous`。

### 2.4 最值钱的数据已在库里

`reviews` 表（`services/review_store.py:13`）整条记录以 JSON 存 `payload` 列，包含：

- `score` / `total_score` / `rating` / `word_count`
- `dimensions`（各维度得分与满分）
- `analysis`：固定五方面 `content / structure / language / technique / emotion`
- `overall_comment` / `highlights` / `suggestions`
- `scoring_basis.requirement_checks`：逐条核对的题干要求与满足情况
- `input.grade` / `input.title` / `input.requirements` / `essay_type`

这是构建学生画像**唯一可靠的来源**，且已经带 `owner` 与 `created_at`。

### 2.5 现有基础设施可复用情况

| 设施 | 位置 | 能否用于记忆 |
|---|---|---|
| SQLite（记录 + 乐观锁） | `services/review_store.py` | ✅ 直接沿用同一 `owner` 口径 |
| 后台线程模式 | `services/review_workbench.py:147,185` | ✅ 异步提炼照抄 |
| 模块级缓存 + mtime | `utils/standard_loader.py` | ✅ 画像读缓存的范本 |
| 内存 LRU + TTL | `utils/cache.py` | ⚠️ **当前是死代码**，全项目零引用 |
| Chroma 向量库 | `rag/vector_store.py` | ❌ 见下 |

**Chroma 不适合承担记忆检索**：`get_retriever()`（`vector_store.py:27-28`）没有 metadata filter 能力，无法按用户隔离；`load_document()` 只读取 `data_path` 下的 `.txt`，是为静态知识库设计的。而画像查询的模式是 `WHERE owner = ?` 精确取，**不是语义相似**——为它上向量库是把简单问题复杂化。

## 3. 三层记忆模型

| 层 | 存什么 | 载体 | 注入预算 |
|---|---|---|---|
| **对话记忆**（工作记忆） | 最近若干轮问答原文 | 复用 `history/*.json` | ≤ 6 条消息，合计 ≤ 2000 字符 |
| **学生画像**（长期记忆） | 弱项维度得分率、反复出现的通病、进步轨迹 | 新建 `memory_profile` 表 | 固定 300~500 token |
| **情节记忆**（事件记忆） | 单篇作文的题目、分数、当时批语 | 复用 `reviews` 表 | 按需取最近 3 篇 |

三层的职责边界必须清晰：**混在一起是记忆系统失败的头号原因**。对话记忆解决"接着刚才说"，画像解决"因材施教"，情节记忆解决"上次那篇"。

---

## 4. 架构：写入与读取是两条不重叠的路径

```
写入：批改完成 ──► 异步提炼 ──► 写入画像表
      (grade() 落库后触发)      (后台线程，不占用用户等待时间)

读取：学生提问 ──► 取画像与近况 ──► 拼进提示词
      (/chat 入口)   (按 owner 精确取)   (不动 system prompt)
```

两条路径**靠存储解耦**，互不依赖对方的执行时机。

## 5. 存储设计

### 5.1 画像表

```sql
CREATE TABLE IF NOT EXISTS memory_profile (
    owner      TEXT NOT NULL,              -- 账号隔离，与 reviews 表同口径
    student    TEXT NOT NULL DEFAULT '',   -- 空串 = 该账号整体画像
    version    INTEGER NOT NULL DEFAULT 1,
    profile    TEXT NOT NULL,              -- JSON，见 5.2
    source_max INTEGER NOT NULL DEFAULT 0, -- 已提炼到的 reviews rowid 水位线
    updated_at TEXT NOT NULL,
    PRIMARY KEY (owner, student)
);
```

`source_max` 是整个设计的关键：提炼时只读取 `rowid > source_max` 的新记录，**增量更新**画像，而不是每次回扫全部历史。批改累计到 50 篇时，这个差别就是"0.5 秒"与"30 秒"。

`version` 字段沿用 `reviews` 表的乐观锁做法（`UPDATE ... WHERE version = ?` + `rowcount` 校验），避免两个提炼线程互相覆盖。

### 5.2 画像 JSON：存结构化字段，不存自然语言长摘要

```json
{
  "n_reviews": 12,
  "weak_dims": {"语言": 0.82, "结构": 0.91},
  "recurring_issues": ["开头常以天气起笔", "论据只有事例、缺分析"],
  "strengths": ["选材真实"],
  "trajectory": ["38", "40", "43"]
}
```

选择结构化字段的三个理由：

1. **可增量** —— 新数据只更新计数与均值，无需重读历史。
2. **不漂移** —— 自然语言摘要每次重写都会变，学生看到的画像会忽左忽右。
3. **可编辑** —— 前端能做成勾选框让教师删除某条错误的"通病"，长摘要做不到。

注入时再渲染成一句话：

> 该生已批改 12 篇。语言维度平均得分率 82%（最弱），常见问题「开头以天气起笔」。近三次得分 38→40→43，呈上升趋势。

### 5.3 对话记忆的裁剪模块

`utils/chat_memory.py`（P0 已实现），全部上限在服务端强制：

| 常量 | 值 | 含义 |
|---|---|---|
| `MAX_MESSAGES` | 6 | 最多保留的消息条数（约 3 轮问答） |
| `MAX_CHARS_PER_MESSAGE` | 500 | 单条正文最大字符数 |
| `MAX_TOTAL_CHARS` | 2000 | 全部记忆正文合计上限 |

裁剪顺序：丢弃非法条目 → 单条截断 → 只取最近 6 条 → 从最旧一侧收敛总长度。

**任何非法输入都退化成空列表，绝不抛异常** —— 记忆缺失不该让对话失败。

## 6. 注入点

| 注入位置 | 改什么 | 价值 |
|---|---|---|
| `agent/tools/react_agent.py` `execute_stream` 的 `input_dict` | 历史作为真实多轮消息前置 | **P0 已实现**，改数据不改结构 |
| `services/review_grader.py` 的批改 prompt | 加一段画像 | **产品价值最高**，评语能说"上次提到的结构问题这次改善了"，且**不增加额外模型调用** |
| `services/consultation_service.py` `_build_consultation_prompt` | 加画像段 | 咨询因材施教 |

### 为什么用真实消息而不是拼字符串

走 Agent 主路径时，历史以 `{'role': 'user'|'assistant', 'content': str}` 形式**前置进消息数组**，让模型能区分「学生说的」与「老师此前回答过的」。只有无法传递消息数组的降级路径（直接 `invoke(prompt)`）才退化为把历史渲染成文本块。

两条路径**不能同时注入**，否则同一段上下文会进两遍。

## 7. P0 实现记录（已完成）

### 7.1 目标

让咨询链路具备上下文衔接能力。**不改表结构，当天可验证。**

### 7.2 改动清单

| 文件 | 改动 |
|---|---|
| `utils/chat_memory.py` | **新建**。`normalize_history()` 裁剪 + `build_history_block()` 文本渲染 |
| `agent/tools/react_agent.py` | `execute_stream(query, history=None)` / `execute(query, history=None)`；`input_dict` 由单条消息改为「历史 + 当前问题」 |
| `services/consultation_service.py` | `answer_consultation` / `answer_question` / `_generate_ai_response` / `_build_consultation_prompt` 四层透传 `history`；Agent 主路径用真实消息，两条降级路径用文本块 |
| `api.py` | `/chat` 读取 `data['history']` 并经 `normalize_history` 强制裁剪后传入 |
| `src/components/MainPage.vue` | 新增 `buildConsultationHistory()`；`sendConsultation` 随请求带回最近轮次，**并补上此前漏传的 `X-Username` 请求头** |

### 7.3 数据来源的选择

P0 采用**前端随请求带回本会话最近轮次**，而不是后端按 `chat_id` 回读 `history/*.json`。理由：

- `/save_history` 在 `finally` 中触发（`MainPage.vue:440`），服务端文件在时序上滞后；一旦同步失败，记忆就静默失效。
- 前端 `messages.value` 就是当前会话的准确全量，零额外请求、零时序依赖。
- 客户端可控带来的风险由服务端 `normalize_history` 的长度与轮次上限兜住；单用户本地场景可接受。

P1 引入服务端画像后，长期记忆将走服务端权威存储，与前端的短期上下文分离。

### 7.4 接口契约变化

`POST /chat` 请求体新增可选字段：

```jsonc
{
  "message": "本次提问",
  "essay_type": "",
  "history": [                        // 可选，缺失时行为与改造前完全一致
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

请求头 `X-Username` 现在是**必需**的（此前缺失时静默落到 `anonymous`）。

### 7.5 自检结果

- 4 个 Python 文件语法编译通过
- 裁剪逻辑边界用例 8/8 通过：非列表输入、非法条目、空正文、超轮次（10→6 条）、超长单条（900→506 字符）、合计收敛（8×480 → 4 条 1920 字）、顺序保持、空历史返回空串
- 图像（`_p0_check.py`）为临时自检脚本，验证后已删除

### 7.6 回滚方式

所有改动均为**向后兼容的可选参数**：`history=None` 时行为与改造前完全一致。回滚只需移除 `/chat` 中的 `history` 传参。

## 8. 反模式：明确不要做的五件事

1. **不要让模型自己决定记什么。** `get_user_id` 那种 tool 式记忆就是这个思路的教训。记忆写入必须是**确定性的副作用**（批改落库就提炼），不是模型的选择。
2. **不要把全量历史塞进 prompt。** `history/*.json` 上限 100 条，全塞必炸。
3. **不要为记忆上向量库。** 画像查询是 `WHERE owner = ?` 精确取，不是语义相似。
4. **不要在请求路径里同步提炼。** 批改已实测约 36 秒（`config/rag.yaml:15`），再加一次模型调用用户会疯。用后台线程，复用 `review_workbench.py:147` 的模式。
5. **不要跳过"查看 / 删除我的记忆"接口。** 记忆系统没有可见性就是隐患，且画像类数据的可删除性有合规要求。

## 9. P1 设计

### 9.1 提炼流程

```
grade() 返回并落库
   └─► 后台线程提炼（复用 review_workbench 的线程模式）
         ├─ 读取 rowid > source_max 的新记录（增量）
         ├─ 一次轻量模型调用，把 review 结果归一化成结构化字段
         ├─ 乐观锁更新 memory_profile
         └─ 推进 source_max
```

提炼的输入是**已结构化的批改结果**，不是原始对话——这是控制成本与噪音的关键。

### 9.2 前提问题（必须先决策）

现在 `owner` 是登录账号（教师），一篇作文归在教师名下，**"记住这个学生"在数据模型上还不成立**。两条路：

- 若目标场景是学生自己登录 → 直接把 `owner` 当学生账号用，无需改表。
- 若是教师批改多个学生 → 给 `reviews` 表加 `student` 字段，并在 `ReviewStore` 的读写中一并带上。

**这个决定要在写 P1 之前定下来**，否则 `memory_profile.student` 会变成一个填不满的空列。

### 9.3 其他待办

- `review_grader.grade()` 的 prompt 加入画像段（价值最高、零额外调用）
- 画像带 TTL 或失效策略：长期不批改的学生，画像里的"近期得分"会误导模型
- 复用 `utils/cache.py` 早已写好的 LRU + TTL 缓存画像读取（该模块目前仍是死代码）

## 11. 附：本设计与既有技术选型的一致性

- **不上 Redis**：记忆读写都在单进程内完成，读取是本地 SQLite 精确查询。与《Redis 适用性评审》的结论一致——只有部署形态变成多进程/多机时才需要集中式存储。
- **不上向量库**：见 §2.5。
- **沿用乐观锁**：`memory_profile.version` 与 `reviews.version` 同一套机制，不引入新的并发控制方案。
- **沿用后台线程**：与 `review_workbench` 的任务模式一致，不引入 Celery/RQ。
